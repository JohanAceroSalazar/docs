# Decisiones internas — audit-service

> Estado: 🟢 Estable | Última actualización: 2026-10-11
> Para decisiones que afectan más de un servicio → crear ADR en `05-architecture/decisions/records/`

| # | Decisión | Alternativas descartadas | Motivo | Fecha |
|---|----------|--------------------------|--------|-------|
| 01 | Tabla única `audit_record` append-only para todos los eventos (sin tablas por tipo de entidad) | Una tabla por tipo de entidad (`audit_class_session`, `audit_enrollment`, etc.); tabla por servicio origen | Tablas por tipo de entidad requieren una migración de BD cada vez que se añade un nuevo servicio o evento. La tabla única con `payload JSONB` permite almacenar cualquier evento sin cambio de esquema. El trade-off de queryabilidad (las queries sobre campos dentro del JSONB son más lentas que sobre columnas tipadas) se acepta: las consultas de auditoría son infrecuentes, de baja concurrencia y toleran mayor latencia | 2026-06-20 |
| 02 | audit-service se suscribe al exchange global `audit-events` con la cola durable propia enlazada mediante `#` | Lista explícita de exchanges; descubrir exchanges por nombre | RabbitMQ no permite descubrir exchanges con wildcard. El exchange global entrega cualquier evento nuevo al worker sin cambios de código ni una lista cerrada de productores | 2026-10-11 |
| 03 | `audit_event_seen.event_id` es la reserva global de idempotencia y se inserta antes de `audit_record` en la misma transacción | Exactly-once del broker; deduplicación fuera de transacción | RabbitMQ es at-least-once. `ON CONFLICT DO NOTHING` permite que solo un consumidor gane; si falla el INSERT append-only, el rollback elimina la reserva y permite reintento sin falso duplicado | 2026-10-11 |
| 04 | audit-service no expone API HTTP (solo consume del broker) | API REST de consulta sobre `audit_db`; API GraphQL para queries flexibles sobre el log | Exponer una API de escritura sobre audit-service abre la posibilidad de modificar o inyectar registros de auditoría por error o maliciosamente. La ausencia de API HTTP es en sí una garantía de integridad. Si se necesitan consultas sobre el log, se crea un servicio de consulta separado sobre una read replica de `audit_db`, sin tocar el servicio que escribe | 2026-06-20 |
| 05 | Doble timestamp: `event_occurred_at` (cuándo ocurrió en el servicio origen) y `received_at` (cuándo llegó al audit-worker) | Un único timestamp de recepción; un único timestamp del evento | El gap entre `event_occurred_at` y `received_at` es información operacional valiosa: detecta lag del broker, retrasos en procesamiento, y permite reconstruir la secuencia real de eventos de negocio independientemente del orden de llegada. Usar solo `received_at` oculta el lag; usar solo `event_occurred_at` impide detectar cuándo el audit-worker estuvo caído | 2026-06-20 |
| 06 | Retención de 7 años (pendiente confirmación legal) con particionamiento mensual por `received_at` | Retención indefinida sin particionamiento; retención de 3 años; particionamiento anual | La normativa de trazabilidad del SENA apunta a 7 años; se mantiene como valor conservador hasta confirmación jurídica formal. El particionamiento mensual (PostgreSQL declarative partitioning RANGE) permite mover particiones antiguas a tablespace cold sin afectar las consultas sobre datos recientes. Particionamiento anual genera particiones demasiado grandes para gestionar individualmente | 2026-06-20 |
| 07 | Archivado a cold storage después de 2 años activos en la tabla principal | Mantener todo en hot storage los 7 años; archivar después de 5 años; purgar en lugar de archivar | Los 2 primeros años concentran el 95% de las consultas de auditoría operacional (investigaciones de incidentes recientes, revisiones de acceso). A partir del año 3, el acceso es esencialmente solo para cumplimiento legal. Mover particiones mensuales a tablespace cold después de 24 meses reduce el tamaño del índice activo y el costo de almacenamiento hot, sin eliminar los registros que la normativa requiere conservar | 2026-06-20 |
| 08 | audit-service no publica eventos propios al broker | Publicar un evento `audit.record.created` por cada registro almacenado; publicar eventos de alerta sobre patrones detectados | Un servicio que registra eventos de otros servicios y a su vez publica eventos crea una dependencia circular: si otro servicio consume `audit.record.created` y su acción genera un nuevo evento, el ciclo no termina. Adicionalmente, publicar eventos desde un servicio append-only viola su invariante: el audit-service es un sumidero, no un productor | 2026-06-20 |
| 09 | HU-AUD-001 entrega el contrato OpenAPI y la base de seguridad; los handlers funcionales de consulta y exportación se entregan en HU-AUD-003/HU-AUD-004 | Implementar endpoints de consulta/exportación incompletos en HU-AUD-001 | El contrato posterior de `audit-query-api` supera la decisión 04 únicamente para lectura. Para evitar comportamiento ficticio, HU-AUD-001 no expone handlers de negocio: deja contrato, puertos y JWT preparados; HU-AUD-003 implementa consulta y HU-AUD-004 exportación | 2026-10-11 |
